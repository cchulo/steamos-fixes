# Surviving SteamOS updates

How steamos-fixes keeps working across SteamOS A/B updates (plan §4.3,
§4.5), the update policy, what you see, and the two documented exceptions
to the "only add drop-ins" rule (plan §4.4). Code: `lib/slots.sh`,
`lib/rauc.sh`, `lib/grub.sh`, `lib/status.sh`, `components/update.sh`,
`cmd/{apply,boot,boot-entry,notify,rauc-handler,update-policy}.sh`,
`overlay/rauc/*.hook`, `overlay/systemd/*.service`.

## What a SteamOS update does (from steamos-customizations 3.9)

Read from `steamos-customizations-jupiter-3.9.20261021.1`
(`/usr/lib/rauc/post-install.sh`, `/usr/lib/holo/holo-sync-var`,
`/usr/lib/rauc/atomic-update-keep.conf`, `holo-chroot`,
`holo-finalize-install`), not assumed:

| partition | mounted at | per slot? | contents |
|---|---|---|---|
| `esp` | `/esp` | shared | `steamcl.efi` chainloader, `/esp/SteamOS/conf/{A,B}.conf` (`holo-bootconf`) |
| `efi-A`, `efi-B` | `/efi` | **per slot** | stage-2 GRUB: `/efi/EFI/steamos/grubx64.efi` and `grub.cfg` (kernel cmdline + initrd list) |
| `rootfs-A`, `rootfs-B` | `/` | **per slot** | read-only image, `/boot/vmlinuz-linux-neptune-72`, `/boot/initramfs-linux-neptune-72.img` (named after the kernel package) |
| `var-A`, `var-B` | `/var` | **per slot** | holds the `/etc` overlay upper dir `/var/lib/overlays/etc/upper` |
| `home` | `/home` | shared | everything else; `/opt`, `/var/log`, … are offloaded here |

1. RAUC writes the new rootfs to the other slot.
2. The stock post-install handler reformats the other slot's `var` and runs
   `holo-sync-var all`: it rsyncs the booted `/var` into it **and prunes
   the `/etc` overlay upper directory to a keep list**. Everything in
   `/etc` not matched by `/usr/lib/rauc/atomic-update-keep.conf` or a
   `/etc/atomic-update.conf.d/*.conf` drop-in is dropped (a backup goes to
   `/var/lib/steamos-atomupd/etc_backup`). The default keep list covers
   `/etc/systemd/system/*.service` and `*.wants/**`, users and groups,
   hostname, machine-id, NetworkManager, ssh keys, the atomupd
   preferences… and **not** `/etc/modprobe.d/*`, `/etc/default/grub.d/*`,
   `/etc/<project>/**`, `/etc/systemd/user/*` or `/etc/rauc/*`.
3. It then runs `holo-chroot --partset <new> -- holo-finalize-install
   --no-kernel`, which regenerates the new slot's `grub.cfg` with
   `update-grub` **after** the sync, so a kept `grub.d` drop-in is
   honoured natively.
4. Only then does our chained post-install handler run.

Consequences:

- **Keep list.** The `update` component installs
  `/etc/atomic-update.conf.d/steamos-fixes.conf` listing every `/etc` path
  we own: `/etc/steamos-fixes/**`, `/etc/modprobe.d/steamos-fixes-*.conf`,
  `/etc/default/grub.d/steamos-fixes-*.cfg`,
  `/etc/systemd/user/steamos-fixes-*.service` and their `.wants` links,
  plus any manifest path those globs do not cover (generated; `status`
  reports `stock` when it is stale and the boot service regenerates it).
  `/etc/rauc/system.conf` is deliberately **not** kept: it must follow
  Valve's version, and our block is re-added for the new slot by the
  post-install handler.
- **State.** `/var/lib/steamos-fixes` is a relative symlink to
  `/home/.steamos-fixes` (shared partition, large). The symlink is a tiny
  file in `var`, carried by the rsync and re-created by `apply --slot`.
  Both slots therefore see the same manifest, backups, cache and checkout.
- **Boot entry.** The new slot's `grub.cfg` is regenerated by Valve; our
  kernel argument comes back through the kept drop-in. The early initrd
  token (only when the initramfs loads a patched module) is not a drop-in
  and is re-applied by our handler.
- `docs/etc-survival.md` holds the **measured** answer from a real update
  on the device; the above is what the scripts say they do.

## How an update flows

```
Steam: "update available"
  └─ steamos-atomupd → rauc install <bundle>
       ├─ pre-install  = /var/lib/steamos-fixes/libexec/rauc-pre-install.hook
       │    1. steamos-fixes.sh rauc-handler pre-install
       │         self-update (if that command exists; once, then re-exec)
       │         incoming kernel version?  ── unknown → let it through
       │         modules for it present?   ── yes → let it through
       │         rebuild --kver (if that command exists; failure cached per kver+commit)
       │         still none → update-policy:
       │              degrade (default) → exit 0, state/pending-rebuild
       │              block   (opt-in)  → exit 1, RAUC aborts, state/update-blocked
       │    2. chained stock pre-install handler
       ├─ RAUC writes the new rootfs to the other slot
       └─ post-install = /var/lib/steamos-fixes/libexec/rauc-post-install.hook
            1. chained stock post-install handler (var sync + /etc prune to the
               keep list, holo-finalize-install → update-grub for the new slot);
               if it fails we stop and return its status
            2. steamos-fixes.sh rauc-handler post-install
                 mount the new slot as a composite root under /run/steamos-fixes/slot-<X>
                   (rootfs ro, its var, /etc overlay on that var, its efi, shared esp/home/opt)
                 stage modules for its kernel into it if we have them
                 apply --slot <root>  (every fix decides from that slot's kernel:
                                       hdmi-frl keeps or removes its grub.d drop-in;
                                       update re-registers RAUC, keep list, boot entry)
                 write state/pending-reboot-check in the new slot
                 release the mount; if a fix changed a drop-in there:
                   holo-chroot --partset <X> -- update-grub
               failures are logged, never fail the update
reboot into the new slot
  └─ steamos-fixes.service  (system, before the display manager, ≤15 s)
       steamos-fixes.sh boot:
         apply --missing-only     re-apply drifted components (files, RAUC block, keep list, boot entry)
         pending grub regeneration for this slot? → update-grub
         modules for uname -r?    no → systemd-run a detached rebuild (next boot)
         probes → state/status.json
         summary → state/notify (consumes pending-reboot-check)
  └─ steamos-fixes-notify.service  (user, after login)
       one notification: updated / re-applied / pending rebuild / degraded / superseded
```

The hooks are self-contained: if the checkout is missing they still run the
chained stock handler and never block, so steamos-fixes cannot be the
reason an update fails except through the explicit `block` policy.

### The pre-install gate may not know the kernel version

SteamOS bundles carry `rootfs.img.caibx` (a casync index), not a mountable
image, so the incoming kernel version is usually not readable before
installation. `rauc_incoming_kver` honours `SOF_INCOMING_KVER` and looks
for a `kernel-version=`-style hint in the bundle manifest; otherwise the
gate lets the update through and post-install + the boot service handle
modules (the version-gated hook keeps the new kernel bootable on stock
modules). Under the default `degrade` policy this changes nothing.

## Update policy: degrade by default

```sh
steamos-fixes.sh update-policy              # show (default: degrade)
sudo steamos-fixes.sh update-policy block   # opt in: hold an update back when no modules can be built
sudo steamos-fixes.sh update-policy degrade # back to the default
sudo steamos-fixes.sh update-policy degrade --once   # under block: let the next update through
```

The sibling project blocks by default because a missing module there means
no speakers and no controller. Here a missing module means "HDMI 2.0 with
VRR instead of HDMI 2.1", so an update always goes through. Stored in
`/var/lib/steamos-fixes/state/update-policy` and `update-policy-once`.
Under `block`, a failed build is cached per kernel version and checkout
commit, so Steam's periodic retries do not rebuild until `self-update`
brings a new commit.

## What you see

- Known kernel: update as usual, reboot, one "re-applied" notification.
- New kernel with a release asset: the handler stages it; the fix is
  `active` after the reboot.
- New kernel without one: the fix is `degraded` (stock behaviour) until the
  background build finishes, a notification, then a second reboot.
- Blocked update (opt-in policy `block`, no fix yet): Steam reports the
  update failed; the notification after the next boot says why and how to
  override.
- Something superseded by SteamOS: a notification; the fix retires its
  non-module parts by itself (`hdmi-frl` removes its kernel argument);
  `uninstall --superseded` removes the rest.

`state/status.json` has the same information for scripts.

## Exception 1: the boot entry

`/efi/EFI/steamos/grub.cfg` is a stock-generated file, per slot. Two of our
mechanisms touch it, never the same text:

- **Kernel arguments** go through `/etc/default/grub.d/steamos-fixes-<fix>.cfg`
  and SteamOS's own `update-grub` (`lib/grub.sh`). Before the first
  regeneration the untouched `grub.cfg` of the slot is saved to
  `/var/lib/steamos-fixes/backup/grub/<slot>/` with its sha256 and
  refreshed whenever the stock file is found unmodified again. For a slot
  that is not booted, the regeneration is noted and run by the RAUC handler
  through `holo-chroot --partset <slot> -- update-grub`, or by the boot
  service on that slot's first boot. Uninstall removes the drop-in,
  regenerates, and reports whether the result is byte-identical to the
  saved copy (it is unless SteamOS changed the stock file in between);
  without `update-grub` the saved copy is restored.
- **The early initrd override** (modules the initramfs loads) is one
  `initrd` token appended after the stock initramfs plus marker comments,
  edited in place by `lib/slots.sh` with the sibling project's contract:
  original saved with sha256, the rendered file is stripped in memory and
  must reproduce the original byte-for-byte before writing, temp+rename,
  restore from the verified backup or by stripping. `boot-entry
  show|set|clear|apply|restore` exposes it.

A copy of `uninstall/efi-cleanup.sh` sits next to each entry we modified as
`/efi/EFI/steamos/steamos-fixes-cleanup.sh`, and
`steamos-fixes-reset-cleanup.service` runs it on both slots at shutdown
when a factory reset is pending ([uninstall.md](uninstall.md)).

## Exception 2: `/etc/rauc/system.conf` (`lib/rauc.sh`)

RAUC reads one `system.conf` and has no `conf.d`, so our handlers have to
go into the stock file. Two programs parse it: RAUC itself (GLib's
GKeyFile, lenient) and `steamos-atomupd-client` (Python `configparser` in
strict mode): a second `[handlers]` section or a repeated key kills every
`steamos-update` check. So the written file has exactly one `[handlers]`
section and each key in it once: our block goes right after the stock
header, and each stock `pre-install=`/`post-install=` line is replaced in
place by a block that keeps the original line as a prefixed comment, which
our hooks chain:

```
[handlers]
# >>> steamos-fixes managed block (sep=0); original saved as /var/lib/steamos-fixes/backup/rauc/system.conf; ...
# stock handlers are chained, see /var/lib/steamos-fixes/state/rauc-chain
pre-install=/var/lib/steamos-fixes/libexec/rauc-pre-install.hook
post-install=/var/lib/steamos-fixes/libexec/rauc-post-install.hook
# <<< steamos-fixes
bootloader-custom-backend=/usr/lib/rauc/bootloader-custom-backend.sh
# >>> steamos-fixes stock handler, chained by the block above
#steamos-fixes-orig:pre-install=/usr/lib/rauc/pre-install.sh
# <<< steamos-fixes
# >>> steamos-fixes stock handler, chained by the block above
#steamos-fixes-orig:post-install=/usr/lib/rauc/post-install.sh
# <<< steamos-fixes
```

Stripping drops the block lines and puts the `#steamos-fixes-orig:` lines
back without the prefix, so the result is the original byte-for-byte.
`apply` renders the file from the stripped original and writes only when
the live file differs. Removal restores the saved original after checking
its sha256; if the stock file changed under our blocks, only the blocks are
removed. A SteamOS update gives the new slot a stock `system.conf` (not on
the keep list, by design); post-install re-registers there and the boot
service repairs it.

## Device checklist (update survival)

1. Install, `systemctl status steamos-fixes.service`, `rauc status`,
   `cat /etc/atomic-update.conf.d/steamos-fixes.conf`.
2. Check the block in `/etc/rauc/system.conf` and the argument in
   `/proc/cmdline` after a reboot.
3. `measure-etc-survival.sh before` (vm/guest), then a real update
   (`steamos-update`) and watch `journalctl -u rauc -f`: our pre-install
   and post-install lines, the chained stock handler, the
   `holo-chroot ... update-grub` line.
4. Before rebooting: mount `/dev/disk/by-partsets/other/{var,efi}` and
   check `state/pending-reboot-check`, the new `grub.cfg`, our `/etc` files
   in the other var's overlay upper.
5. Reboot, check the notification, `status.json`, `rauc status`,
   `hdmi-frl status`; fill in [etc-survival.md](etc-survival.md).
6. Repeat with the network blocked (degrade path) and, once, with
   `update-policy block`.
7. `uninstall`: `system.conf` byte-identical to the saved original,
   `grub.cfg` regenerated and compared.
